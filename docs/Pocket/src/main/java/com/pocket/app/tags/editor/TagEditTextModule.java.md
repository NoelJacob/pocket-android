# Pocket/src/main/java/com/pocket/app/tags/editor/TagEditTextModule.java
## What this is — the adapter between the tag editor's chip input field (the box where selected tags appear as removable tokens) and the `TagModuleManager`. It translates typing into filter events, chip commits into add events, and chip deletions into remove events — and applies every other module's changes back into the field as chips. It owns no tag data itself.
## How it fits — constructed in `ItemsTaggingFragment.addChipEditTextModule` around the fragment's `ChipEditText` (a text field that renders completed entries as chips). It registers a text watcher (a callback fired on every keystroke) that forwards input to `manager.onTagInputTextChanged`, a validator from `manager.getTagValidator()` (rejects reserved names and over-long tags), and a chips listener mapping commit/delete/error to manager calls. The manager calls back into `onTagAdded`/`onTagRemoved`/`onTagsLoaded` to keep the field mirroring selections made elsewhere (tapping the list, suggestions, recents).
## Key pieces — Constructor wiring (text watcher + validator + `ChipInputCommitListener`): the three translations typing→filter, commit→add, delete→remove, error→`manager.setError`; WHY: every user gesture in the field becomes exactly one manager event. `onTagAdded(tag)`: clears pending text and adds the chip; WHY: picking a tag elsewhere must appear in the field and reset the autocomplete input. `onTagRemoved(tag)`: removes that chip; WHY: un-picking anywhere (e.g. tapping a selected chip in the list) must vanish from the field too. `onTagsLoaded(allTags)`: swaps in the "no tags yet" hint when the user owns none; WHY: first-run guidance lives here, not in layout XML. `load(callback)`: reports loaded immediately; WHY: no async work, but still part of the manager's load gate.
## Junior notes — The `afterTextChanged` copy (`subSequence`, not the live `Editable`) matters: forwarding the mutable object would let downstream listeners accidentally edit the field's text. `onTagInputTextChanged` is intentionally empty — this module produces input events but never consumes them (it must not filter itself). Validation errors surface via the manager's error path (a snackbar), not inline — do not add a second error display here.
