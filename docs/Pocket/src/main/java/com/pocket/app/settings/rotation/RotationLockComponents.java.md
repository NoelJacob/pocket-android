# Pocket/src/main/java/com/pocket/app/settings/rotation/RotationLockComponents.java
## What this is — the coordinator that decides when the rotation-lock button appears. While unlocked it watches for screen rotations and pops the button up; while locked it watches the device sensor for a new orientation so the user can unlock. It also suppresses the whole feature when the user disabled it in settings or when the OS-level rotation lock is on.
## How it fits — instantiated per activity with the activity, the user's enable/disable `BooleanPreference` (a persisted true/false setting), an `OSRotationLock` observer, a `RotationLockView` (the floating button), a `FineOrientationManager` (sensor listener for small orientation changes), and the `RotationLock` state holder. It plugs into `AbsPocketActivity` lifecycle callbacks (`onActivityResume`/`onActivityPause`/`onActivityDestroy`) and `onConfigurationChanged` (the framework callback Android fires when rotation actually happens). Tapping the button flows back through `RotationLock.setLocked()`.
## Key pieces — constructor wiring: subscribes to the user-pref changes (auto-unlocks if the setting is turned off mid-lock), registers the sensor callback to re-show the button, and registers the toggle-click handler; WHY: all three event sources funnel into one place so they cannot disagree. `isLockingAllowed()`: always true when already locked (need an escape hatch), otherwise requires the setting enabled AND no OS lock; WHY: prevents showing a button that could not work. `setupCurrentOrientation()`: on start/restart, re-applies the saved lock if the activity's orientation drifted; WHY: keeps the lock sticky across screen navigations. `onConfigurationChanged()`: compares old vs new orientation and posts a `lockView.show()` if they differ; WHY: the "just rotated, offer to lock" trigger. Lifecycle methods: enable the sensor listener only while resumed and locked, start/stop OS-lock observing with the screen, dispose the prefs subscription on destroy; WHY: no battery drain or leaks from background listeners.
## Junior notes — `Handler.post()` here means "run this on the main (UI) thread next loop" — required because prefs callbacks can arrive off-thread. `Disposable` (from RxJava, a reactive-streams library) is the subscription handle; `dispose()` unsubscribes, and forgetting it leaks the activity. The OS lock check matters: when the system rotation lock is on, Pocket cannot override it, so the in-app button stays hidden by design.
