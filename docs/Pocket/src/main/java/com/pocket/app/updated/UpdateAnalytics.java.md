# Pocket/src/main/java/com/pocket/app/updated/UpdateAnalytics.java
## What this is — a tiny analytics ping sent once per app upgrade: it records which version the user came from and which they moved to, as a `pv_wt` (page-view-with-target) event in the `APP_UPGRADE` section. Its only purpose is upgrade-path reporting — seeing how far back real upgrade jumps go so the team knows which old versions must still migrate cleanly.
## How it fits — a Hilt `@Singleton` (one shared instance, constructor params provided automatically) created at app startup with `Pocket` (the sync/analytics gateway), `Versioning` (knows previous vs current version codes), and an `ErrorHandler`. If `versioning.isUpgrade()`, the constructor itself fires `pocket.sync(...)` with the from-version as page and to-version as action id, formatted via `VersionUtil.toVersionName`. Nothing ever calls methods on this class — instantiation is the entire behavior.
## Key pieces — Constructor body: the upgrade check, the `from`/`to` read, and the `pv_wt` sync with `CxtView.MOBILE` / `CxtSection.APP_UPGRADE`; WHY: doing it in the constructor guarantees it runs exactly once at startup with no call site to forget. `try/catch` reporting to `errorHandler` instead of throwing; WHY: analytics must never crash or block launch. The no-`Interaction` comment: the event carries no tap context because interaction tracking is not initialized this early; WHY: documents why this one event looks "bare" compared to others.
## Junior notes — Side effects in a constructor are normally a smell, but here they are the pattern: Hilt creates the singleton at startup and the constructor is the hook. `VersionUtil.toVersionName` converts raw version codes to human names — the dashboard reads those strings, so do not swap in raw ints. If the process dies seconds after upgrade, this event can be lost; that undercounting is accepted, not a bug to retry-loop.
