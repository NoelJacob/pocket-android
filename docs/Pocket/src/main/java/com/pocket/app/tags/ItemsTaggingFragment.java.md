# Pocket/src/main/java/com/pocket/app/tags/ItemsTaggingFragment.java
## What this is — the tag editor screen the user actually interacts with: a chip input field (tokens for each tag) at the top, suggested/recent/all-tags rows below, and a Save button. Single-item mode edits one article's tags (replace on save); multi-item mode bulk-adds the chosen tags to every selected article. It also handles rotation-safe state restore, an unsaved-changes guard, and save confirmations.
## How it fits — shown via `show(activity, items, addOnly, cxts)`, which uses dialog mode on large screens (`FormFactor.showSecondaryScreensInDialogs`) or `ItemsTaggingActivity` otherwise. On create it builds a `TagModuleManager` (the central tag-selection state + module coordinator) plus one `TagModule` per UI section (chip editor, suggestions, recents, full list, add-new, empty state), loads the user's tags through the sync engine (`pocket().sync`), and on save fires `tags_replace` (single) or `tags_add` per item (bulk) with analytics context. Back press and up-navigation route through an unsaved-changes dialog.
## Key pieces — `newInstance(items, addOnly, cxts)` + `copyAndReduceItemsForParcel`: parcel only identities (plus the first item's full state) to avoid oversized-transaction crashes; WHY: bulk tagging can carry many items. `onActivityCreated`: resolves single vs multi mode, wires the chip field (lowercase filter, auto-scroll), creates the manager with error/modified/loading callbacks, sets up the `RecyclerView` (a scrollable list that recycles row views) with animations disabled (they looked janky with dynamic modules), and pre-selects the item's existing tags; WHY: the whole screen assembly in one method. `onCreateModules` + `addXModule` helpers: register each section module with the manager and the adapter, including the sticky "All tags" dual-header trick (one scrolling header plus one pinned copy that appears when the first scrolls off); WHY: each tag source stays an independent plug-in. `saveAndFinish()`: commits pending chip text, sorts tags, syncs replace vs add actions with full analytics counters (opened/entered/suggested/tapped/removed counts), toasts confirmation; WHY: the mode split (replace vs additive) is the core semantic difference. `confirmSaveChanges()` + `finish()`/`onBackPressed()` + `onSaveInstanceState`: guard against losing edits and restore selections after rotation; WHY: exits always funnel through the guard.
## Junior notes — `ItemMode` is decided by item count unless `addOnly` forces bulk mode — one item can still be in bulk-add mode. `tagsEditText.commitPending()` must succeed before saving; if it returns false a validation error is already showing and save aborts. Never trust the parceled `items` beyond identities/`id_url` — fresh state comes from `syncLocal`. The save button is enabled by a `ViewEnabledManager` combining "modified" and "not loading", so it is dead until both hold.
