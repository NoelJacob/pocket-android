# Pocket/src/main/java/com/pocket/app/settings/view/preferences/PreferenceViews.java
## What this is — the factory helpers every Settings screen uses to declare its rows without touching preference constructors directly. It offers `newHeader`, `newActionBuilder`, `newImportantBuilder`, `newToggleSwitchBuilder`, and `newMultipleChoiceBuilder`, each returning a builder where you set the title, subtitles, backing setting, enabled condition, and analytics id, then call `build()`. This is the only intended way to create preferences now that the raw constructors are deprecated.
## How it fits — each settings fragment (e.g. the main, notification, cache, and listen fragments under `settings/`) calls these builders in its row-setup method to produce the `List<Preference>` the fragment adapter renders. Tapping a built row flows into the corresponding `ActionPreference`, `ToggleSwitchPreference`, or `MultipleChoicePreference`; toggle and choice builders accept either a raw `BooleanPreference`/`IntPreference` (persisted true/false and number settings) or a custom `PrefHandler` adapter. The `EnabledCondition` parameter on every builder is the "grey this row out when…" rule.
## Key pieces — `newHeader(frag, title[, topDivider])`: one-liner for section dividers; WHY: headers need no builder because they have no behavior. `ActionBuilder` / `ImportantBuilder`: set title, summary texts, tap and long-press actions, enabled condition, analytics id, then `build()` an action or important row; WHY: one builder covers both since an important row is just a restyled action row. `ToggleSwitchBuilder`: wraps a boolean setting with on/off summaries plus an `OnChangeListener` veto/after-change hook; WHY: gives callers a chance to block a toggle (e.g. show a prompt) before it persists. `MultipleChoiceBuilder`: wraps an int setting with parallel choice-label and value arrays; WHY: keeps the dialog list and the saved index aligned by construction. `SettingBuilder` base (with `EnabledCondition`): shared title/condition/analytics plumbing; WHY: every row type needs the same three cross-cutting options.
## Junior notes — Builders are single-use: configure, `build()`, and drop them; the built `Preference` holds copies of your callbacks. If a row needs to change after creation (e.g. new subtitle), mutate the built preference via `updateSummary()` and ask the fragment to refresh — rebuilding the list is unnecessary. `UiEntityIdentifier` parameters are analytics tags for which row was tapped; pass them through, never null them out "to simplify".
