# Pocket/src/main/java/com/pocket/app/undobar/UndoBar.kt
## What this is — the app-wide "Item archived — UNDO" bar. After an archive or delete it immediately syncs the action to the server, shows a 5-second overlay on whatever screen the user is on (following them across activities), and if they tap Undo, syncs the inverse action. If the bar times out, it releases the retained item data. It is a Hilt `@Singleton` (one shared instance, constructor params provided automatically).
## How it fits — list screens, readers, and bulk-edit flows call `archive(UndoableItemAction(s))` or `delete(item(s))` instead of syncing archive/delete actions themselves. `UndoBar` builds the `Archive`/`Delete` sync actions with analytics context, `remember`s the items in a session `Holder` (a pin keeping synced objects in memory so undo can restore them fully), fires the sync, then shows the UI via `showUndoUi`. Undo taps sync `undo_archive`/`undo_delete` tagged with `CxtUi.UNDO_BAR`. It also implements `AppLifecycle` (app-level lifecycle hooks) so logout dismisses any visible bar.
## Key pieces — `archive(...)` overloads: single `UndoableItemAction` (id + URL + optional context) fans into the list version; bulk vs single picks plural vs singular messages; WHY: one funnel for all archive entry points. `delete(item/cxt)`, `delete(items)`, private `delete(map)`: same shape for deletes, carrying full `Item`s (undo needs the old status) where archive needs only ids; WHY: `undo_delete` must restore `old_status`, so the original items are required. `showUndoUi(message, undidMessage, onTimeout, undo)`: hides any existing bar, creates an `UndoBarViewController`, attaches/detaches it on activity resume/pause via an `ActivityMonitor.Listener`, anchors it to the currently visible activity one loop later (in case the action just closed one), starts the timeout, and tracks it in `active`; WHY: the overlay-outlives-navigation behavior lives entirely here. `hideAll()`: finishes every active bar (copying the set first to avoid concurrent-modification); WHY: a new action replaces, never stacks, bars. `onLogoutStarted()` policy: hides bars on both `stopModifyingUserData` and `deleteUserData`; WHY: undoing across an account switch would corrupt the new account. `UndoableItemAction` + `fromTrack`/`fromDomainItem`: the minimal undoable identity (item id, URL, context) with converters from player tracks and article models; WHY: callers in audio vs list contexts both reduce to the same triple.
## Junior notes — Actions sync immediately, not after the timeout — Undo sends a second inverse action; there is no "pending, then commit" queue, so the server briefly sees the archived state even if the user undoes. `Holder.session("undobar_...")` + `pocket.forget` is manual memory management for the restore path: the hold must be released on timeout or the items leak in the sync cache. Coroutines are not involved here; threading is the main-thread `Handler` inside the view controller.
